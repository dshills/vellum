# Conditional Metal frame-latency experiment

A Mac/Metal-only request for `DesiredMaximumFrameLatency: 1` is a justified, narrow next experiment if the current four-case source101 comparison meets cadence but still misses the existing p95 threshold. This is a prospective configuration experiment; source inspection does not establish the cause of current latency or promise improvement. Do not change M3 thresholds or measurement accounting.

The actual pinned path supports it end to end. Core `gpu/surface.go:167` constructs FIFO configuration without that field. Go binding `wgpu/common.go:92` exposes it; `wgpu/surface.go:79–108` sends a pinned native extras chain only for values above zero, synchronously through Configure. Native `source/src/conv.rs:1959–1964` uses the provided value or defaults to 2. Cargo.lock pins core/hal/types 29.0.3. `wgpu-core/.../device/resource.rs:5099–5102` clamps the request to backend capabilities. Metal `adapter.rs:404–415` allows 1..=2 on macOS 10.13.2+ (otherwise 2..=2). Metal `surface.rs:99` configures CAMetalLayer maximumDrawableCount to the clamped latency plus one: request 1 means two drawables; current default 2 means three. The public Go capability object does not expose the latency range; core clamps internally. The pinned types documentation explicitly describes 1 as a low-latency GUI choice with a throughput tradeoff, not a guaranteed presentation deadline.

Keep the experimental change confined to surface configuration on Darwin when the actual adapter backend is Metal (`GPU.Properties.BackendType`); leave other configurations at their present zero/default. Preserve FIFO, dimensions, formats, MSAA, all frame/texture ownership and measured acquisition/presentation paths. Existing resize/lost-surface reconfiguration reuses the same configuration, so a value set at initialization persists without extra frame-time work. No native library rebuild, raw CAMetalLayer mutation, renderer rewrite, new queue, or lifetime changes are needed.

The main risk is where waiting moves. Metal acquisition holds its render-layer mutex while calling nextDrawable; `_timeout` is ignored and `allowsNextDrawableTimeout` is set false (`surface.rs:103–119,159–166`). The existing macOS occlusion check skips known invisible windows, but this does not guarantee bounded acquisition for every stall/race. Core holds its surface mutex through acquisition until present/abort, including the measured path. Fewer drawable slots can therefore increase acquisition blocking, frame-busy retry/backpressure and delays to resize/closure, or reduce throughput when CPU/GPU work exceeds one refresh. Preserve current cleanup and bounded busy-retry behavior; do not compensate with spin/polling, more inflight frames or altered accounting.

After current native ownership is fully retired, implement/review the one config change, run focused actual config/lifecycle checks and the unchanged headless prerequisites, then produce a fresh SDK/binding. Compare the same four serial/paced grid/tree cases, cohorts, sample sizes and strict validator with source101. Inspect both end-to-end p95 and cadence plus acquisition wait, frame-busy/coalescing, input/UI work and shutdown/occlusion behavior. Accept only an actual measured improvement without functional, ownership or cadence regression; otherwise revert the isolated configuration. Existing failed evidence stays failed, and prior native results are never rebound to changed source.
